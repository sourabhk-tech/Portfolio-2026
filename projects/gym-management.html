The brief

The project needed to do two jobs: give the gym a public website and give the team a way to register and manage members. Instead of treating those as separate products, I built them into one ASP.NET MVC application with shared structure and a SQL Server database.

The public side introduces the gym and its services. The member side handles registration, authentication, and a view of the people in the system.

What I built

  • Public pages for home, about, services, gallery, blog, and contact.
  • A member registration flow with a dedicated form.
  • Admin login and a member list for reviewing registrations.
  • A SQL Server database connection for storing member records.

How it’s structured

The application follows the MVC pattern: controllers handle requests, Razor views render the interface, and SQL Server stores the data. Bootstrap provides the responsive base for the public-facing pages, while the admin views stay focused on the task at hand.

The current interface is intentionally functional. The dashboard image at the top of this page is a concept for the reporting layer — a way to show what the system could surface once the data model supports it, not a screenshot of the existing screens.

Outcome

Working Academic system

The finished project does the two jobs it set out to do: present the gym publicly and keep member registration in one database-backed flow. It is a foundation, not a production system.

Reflection

The project taught me where the real risk sits in a management system: not the page that lists members, but the validation, permissions, and backup plan around it. If I rebuilt it, I would start with those constraints and treat the interface as the last layer, not the first.

What I’d take further

The next iteration would add role-based access for staff, payment and attendance tracking, server-side validation across every form, and live reporting dashboards. I’d also want a proper deployment and backup workflow before the system handled real member data.
